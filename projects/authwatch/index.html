authwatch

SSH authentication log analysis and detection engine

The problem

An auth.log on a modestly busy server accumulates thousands of lines a day. Almost all of it is noise. Buried in it are the handful of events that matter: a machine working through passwords, someone testing one password against every account on the box, a credential being used from somewhere it has never been used before.

authwatch reads the log and answers one question — what in here deserves a human's attention?

Architecture

Four modules, one responsibility each. The separation is the point: detection rules are pure functions, so they can be tested without a database, a web server, or a log file.

  • parser.py — the only code that knows log line formats. Emits normalized event records.
  • detections.py — pure functions. Events in, alerts out. No I/O, no printing, no database.
  • store.py — SQLite persistence and queries.
  • api.py / cli.py — two thin interfaces over the same store.

Supporting a new log source — Windows Event Log, CloudTrail — means writing a new parser, not touching a single detection rule.

The rules

RuleSeverityWhat it catches
brute_forceHigh One IP, one account, N failures inside a sliding window.
password_sprayHigh One IP, many distinct accounts, few attempts each.
off_hours_successMedium A successful login outside business hours.
new_ip_successMedium First successful auth from an IP with no prior success history.

Why spray needs its own rule

Brute force counts failures per account. An attacker who tries two passwords against eighty accounts never trips that counter — no single account sees enough failures, which is precisely why the technique works against lockout policies. Spray detection counts distinct usernames per source IP instead. Same data, inverted shape.

Why the sliding window is a deque

Each (ip, user) pair gets a deque of failure timestamps. Push each new failure, pop from the left while the oldest entry falls outside the window, and the window length is the deque length. Every event is pushed and popped at most once, so the pass is linear. The naive alternative — rescanning prior events for each new one — is quadratic and falls over on a real log.

The bug worth writing down

The first version of new_ip_success fired on everything. Three of five alerts against the test data were false positives — office IPs flagged as suspicious.

The cause: the baseline of known IPs was being built from the same window being analyzed. On a first run, no IP has any history, so every IP looks new. The rule was technically working and practically useless.

The fix was a warm-up period. Events inside the first twelve hours of the log build the baseline without raising alerts. Two details make the rule behave now:

  • The baseline is built in timestamp order, so an IP counts as known only from earlier events. Building it from the whole file first means every IP looks known and the rule silently never fires — the same bug in the opposite direction.
  • The warm-up window suppresses the cold-start noise.

After the fix, the only new_ip_success alert remaining on the test data was the genuine one — and it shared a timestamp with an off-hours alert.

What the output actually says

On the test log, the two HIGH alerts are failed attacks: loud, obvious, unsuccessful. The attacker never got in.

The two MEDIUM alerts share a timestamp and an IP. A successful login, outside business hours, from an address that had never authenticated before. Neither rule rates that high on its own.

Severity on any single rule tells you less than correlation across rules. The finding worth investigating was never the highest-severity line.

Testing

36 tests, running in about a tenth of a second — the payoff for keeping detection logic free of I/O. The interesting cases are the negative ones, verifying that rules stay quiet when they should:

  • failures spread beyond the window do not trip brute force
  • failures split across two accounts, or two IPs, do not combine into one alert
  • fifty attempts against a single account do not register as a spray
  • a failed 3am login does not trip the off-hours rule — that is brute force's job
  • every IP inside the warm-up window stays suppressed

A rule that fires on everything is as useless as one that never fires. False-positive behavior is where detection logic actually breaks, so that is where the tests are.

Known limitations

  • The IP baseline lives in a single file rather than persisting across runs. store.py is positioned to hold it; that is the next change.
  • One log source — OpenSSH syslog format. The parser boundary is where a second would plug in.
  • Rules are independent. A correlation layer — brute force followed by a success from the same IP — would be higher-signal than any rule alone.
  • No suppression or tuning workflow, so a noisy rule stays noisy.
